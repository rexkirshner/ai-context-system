# v2.2.0 Plan – Codex Feedback

## High-Level Observations
- The implementation plan’s debt-first sequencing keeps the 10-day window realistic while reinforcing the “simplify first” philosophy (`improvements/v2.2.0-implementation-plan-final.md:26`).
- The before/after comparison effectively communicates the scope reduction to stakeholders and should translate well into release notes (`improvements/v2.2.0-plan-comparison.md:3`).

## Critical Alignment Gaps
- Boundary docs still describe the deprecated 600-line enforcement layer, a new `/init-context-scoped` command, and helper scripts that the final plan explicitly rejects (`improvements/v2.2.0-boundary-feature-summary.md:41`, `improvements/v2.2.0-boundary-feature-summary.md:94`). Reframe this file around the lightweight config flag described in the final plan (`improvements/v2.2.0-implementation-plan-final.md:170`) or archive it as “v2.1 legacy boundaries” so it doesn’t misdirect the build.
- Priority-0 removals target `/save-context`, but `scripts/save-context-helper.sh` and any legacy docs still depend on it (`scripts/save-context-helper.sh:1`). Add an explicit task to delete or repurpose that helper so users aren’t left with a broken entry point.

## Execution Risks & Mitigations
- **Modularization mechanics:** The plan sketches the target folder layout but doesn’t spell out how `/update-context-system` will migrate existing installs into `core/` and `modules/` (`improvements/v2.2.0-implementation-plan-final.md:122`). Document the file moves and guard rails (backups, idempotency) or consider a dry-run mode before touching live projects.
- **Config simplification:** Reducing `.context-config.json` to ~50 lines implies a schema rewrite, yet `config/context-config-schema.json` still enforces the current structure. Schedule schema + template updates together and list validation points so `/validate-context` doesn’t start failing mid-upgrade (`config/context-config-schema.json:1`).
- **Git push guard coverage:** “Add to ALL commands” is broad; enumerate the specific commands that perform git operations and verify none of the remaining scripts invoke `git push` indirectly (`improvements/v2.2.0-implementation-plan-final.md:67`). Pair this with a regression test that confirms `/save` and `/save-full` abort when `PUSH_APPROVED` is false.

## Suggested Enhancements
- Expand the testing plan with a lightweight automation harness (bash + `set -e`) so Day 9 validation is reproducible, not manual (`improvements/v2.2.0-implementation-plan-final.md:332`). Include module toggle scenarios (modules enabled/disabled) and boundary-on/off permutations.
- Call out documentation touchpoints created by the removals: README workflow screenshots, templates that mention QUICK_REF, and any migration guide excerpts that still refer to `/save-context` (`improvements/v2.2.0-implementation-plan-final.md:229`). A checklist will keep Day 10 focused.
- Consider dropping success metrics that can’t be measured automatically (e.g., “Commands to remember”) or note how you will gather the baseline so this doesn’t become hand-wavy (`improvements/v2.2.0-implementation-plan-final.md:276`).

## Open Questions
- When modules are disabled (e.g., `review: false`), should `/update-context-system` prune the associated command files or leave them dormant in place? Clarifying this behavior upfront will drive implementation details (`improvements/v2.2.0-implementation-plan-final.md:151`).
- Do we need a compatibility shim for users who still run `/save-context` until the update lands? If not, we should surface a migration warning so they understand the command is gone before the next release window.

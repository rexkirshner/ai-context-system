## v5.3.0 Candidates (High Priority Deferred)

### ARCH-5: Shell State Persistence in Commands

**Original Priority:** High
**Estimated Effort:** 1-2 days per command
**Source:** v5.2.0 feedback (ALL 3 projects reported this)
**Deferred Reason:** Fundamental architectural change; requires command-by-command refactoring

#### Problem Statement

Each `Bash` tool call in Claude Code creates a new shell session. This causes:

1. **Functions not available** - `common-functions.sh` must be re-sourced in every bash block
2. **Variables don't persist** - `PRE_UPGRADE_VERSION` set in Step 1 is not available in Step 2
3. **Workarounds required** - AI must save variables to temp files and re-source functions
4. **Error-prone execution** - 10+ bash blocks in `/update-context-system` each need manual setup

**User Quote (Project Beta):**
> "The skill instructions assume bash commands share state (variables persist across steps), but Claude Code's Bash tool creates fresh shells."

**User Quote (Project Gamma):**
> "Same issue as previous v5.1.4 upgrade. Still not fixed in v5.2.0."

#### Proposed Solution

**Create consolidated helper scripts:**

```
scripts/
├── upgrade.sh              # Replaces 10+ bash blocks in /update-context-system
├── review-context.sh       # Replaces 10+ bash blocks in /review-context
├── save-full-helper.sh     # Already exists, may need enhancement
└── init-context-helper.sh  # New: handle init in single invocation
```

**Example: `scripts/upgrade.sh`**
```bash
#!/bin/bash
source "$(dirname "$0")/common-functions.sh"

# Single script handles entire upgrade
PRE_UPGRADE_VERSION=$(get_system_version)
# ... all upgrade logic in one invocation
# ... no shell state issues
```

**Command file becomes minimal:**
```markdown
## /update-context-system

Run the upgrade script:
\`\`\`bash
./scripts/upgrade.sh --yes
\`\`\`

The script will:
1. Create backup
2. Download new version
3. Update files
4. Archive feedback
5. Report changes
```

#### Benefits

- **Reliable execution** - No shell persistence issues
- **Faster** - Single bash invocation vs. 10+ round trips
- **Testable** - Scripts can have unit tests
- **Maintainable** - Actual code vs. markdown code blocks

#### Implementation Plan

1. Create `scripts/upgrade.sh` consolidating /update-context-system logic
2. Create `scripts/review-context.sh` consolidating /review-context logic
3. Update command files to invoke scripts
4. Add error handling and logging to scripts
5. Test on all 3 feedback projects
6. Document the change for users

#### Acceptance Criteria

- [ ] `/update-context-system` runs as single bash invocation
- [ ] `/review-context` runs as single bash invocation
- [ ] No "re-source common-functions.sh" workarounds needed
- [ ] Variables persist across logical steps within script
- [ ] All 3 feedback projects confirm improvement

### ARCH-6: /save-full Large File Handling

**Original Priority:** High
**Estimated Effort:** 2-4 hours
**Source:** v5.2.0 feedback (Project Beta)
**Deferred Reason:** Requires skill instruction updates and testing

#### Problem Statement

SESSIONS.md files exceeding 25K tokens cause Read tool failure:
```
File content (48231 tokens) exceeds maximum allowed tokens (25000)
```

The `/save-full` skill doesn't provide guidance for large files, unlike `/review-context` which has smart loading.

**User Quote (Project Beta):**
> "Had to use Bash workarounds (head, grep, tail) to extract session number and recent content."

#### Proposed Solution

**Add to /save-full skill instructions:**

```markdown
### 1. Determine Session Number

**For large SESSIONS.md files (may exceed Read tool limits):**

If Read tool fails with token limit error, use bash:
\`\`\`bash
# Get last session number without reading full file
LAST_SESSION=$(grep -E "^## Session [0-9]+" context/SESSIONS.md | tail -1 | grep -oE "[0-9]+")
NEXT_SESSION=$((LAST_SESSION + 1))
echo "Next session: $NEXT_SESSION"
\`\`\`

**For appending session entry:**
\`\`\`bash
# Append without reading full file
cat >> context/SESSIONS.md << 'EOF'
## Session $NEXT_SESSION | $(date +%Y-%m-%d) | [Title]
...
EOF
\`\`\`
```

#### Implementation Plan

1. Add "Large File Handling" section to save-full.md skill
2. Provide bash-based session number detection
3. Document append-only strategy for large files
4. Test on Project Beta (48K tokens SESSIONS.md)

#### Acceptance Criteria

- [ ] /save-full skill includes large file guidance
- [ ] Session number can be determined without Read tool
- [ ] Session entry can be appended without reading full file
- [ ] Tested on 25K+ token SESSIONS.md

### FEAT-25: Auto-populate Config from package.json

**Original Priority:** Medium
**Estimated Effort:** 4-6 hours
**Source:** v5.2.0 feedback (Project Gamma, Project Alpha)
**Deferred Reason:** Requires init-context and save-full updates

#### Problem Statement

`.context-config.json` has TBD/placeholder values even in active projects:
```json
"urls": {
  "production": "TBD",
  "repository": "TBD"
},
"techStack": "TBD",
"commands": {
  "dev": "TBD",
  "test": "TBD"
}
```

These should be auto-populated from `package.json`:
- `scripts.dev` → `commands.dev`
- `scripts.test` → `commands.test`
- `repository.url` → `urls.repository`
- Dependencies → `techStack`

**User Quote (Project Gamma):**
> "This is a project issue, not ACS issue, but it demonstrates that /init-context didn't populate these from package.json"

#### Proposed Solution

**Add to /init-context Step 5:**
```bash
if [ -f "package.json" ]; then
  echo "📦 Detecting project info from package.json..."

  # Commands
  DEV_CMD=$(jq -r '.scripts.dev // "npm run dev"' package.json)
  TEST_CMD=$(jq -r '.scripts.test // "npm test"' package.json)
  BUILD_CMD=$(jq -r '.scripts.build // "npm run build"' package.json)

  # Repository
  REPO_URL=$(jq -r '.repository.url // .repository // "TBD"' package.json)

  # Tech stack from dependencies
  TECH_STACK=$(detect_tech_stack)  # New function in common-functions.sh

  # Update config
  jq --arg dev "$DEV_CMD" --arg test "$TEST_CMD" \
     '.project.commands.dev = $dev | .project.commands.test = $test' \
     context/.context-config.json > tmp.json && mv tmp.json context/.context-config.json
fi
```

**Add `detect_tech_stack` to common-functions.sh:**
```bash
detect_tech_stack() {
  local stack=""
  [ -f "package.json" ] && {
    grep -q "next" package.json && stack+="Next.js, "
    grep -q "svelte" package.json && stack+="SvelteKit, "
    grep -q "typescript" package.json && stack+="TypeScript, "
    grep -q "prisma" package.json && stack+="Prisma, "
    grep -q "tailwind" package.json && stack+="Tailwind CSS, "
  }
  echo "${stack%, }"  # Remove trailing comma
}
```

#### Implementation Plan

1. Create `detect_tech_stack` function in common-functions.sh
2. Add package.json detection to /init-context
3. Add config validation to /review-context
4. Optionally add config update to /save-full
5. Test on projects with various tech stacks

#### Acceptance Criteria

- [ ] /init-context populates commands from package.json
- [ ] /init-context detects tech stack from dependencies
- [ ] /review-context warns about TBD values with available alternatives
- [ ] Works for npm, pnpm, and yarn projects

### FEAT-26: Code Review DECISIONS.md Cross-Reference

**Original Priority:** Medium
**Estimated Effort:** 4-6 hours
**Source:** v5.2.0 feedback (Project Alpha)
**Deferred Reason:** Requires specialist agent updates

#### Problem Statement

Code review finds issues that are actually documented intentional decisions:
- SEC-001 (CORS wildcard) marked "High" but D009 establishes public API
- Reviewer notes "May be intentional" but still reports as finding

**User Quote (Project Alpha):**
> "The finding correctly notes 'recommend documenting in DECISIONS.md' but didn't detect that D009 establishes this as a public API with open access."

#### Proposed Solution

**Add to codebase-scanner output:**
```json
{
  "activeDecisions": [
    {
      "id": "D009",
      "summary": "Public API with CORS wildcard",
      "patterns": ["Access-Control-Allow-Origin: *", "cors: { origin: '*' }"]
    }
  ]
}
```

**Add to specialist agents:**
```markdown
### Decision Cross-Reference

Before reporting a finding, check if codebase-context.json contains
a matching decision in `activeDecisions`:

1. Search for patterns in the decision
2. If found, check if finding matches the decision's scope
3. If matches:
   - Set severity to "Info"
   - Add note: "Documented in DECISIONS.md: {decision.id}"
   - Move to "Known Tradeoffs" section instead of "Findings"
```

#### Implementation Plan

1. Update codebase-scanner to extract active decisions from DECISIONS.md
2. Update specialist agents to check decisions before reporting
3. Add "Known Tradeoffs" section to audit report format
4. Update synthesis-agent to handle decision-backed findings
5. Test with projects that have documented security decisions

#### Acceptance Criteria

- [ ] Scanner extracts decisions from DECISIONS.md
- [ ] Specialists check decisions before reporting findings
- [ ] Documented decisions appear in "Known Tradeoffs" not "Findings"
- [ ] Finding count excludes intentional decisions

### ARCH-4: Code Review Orchestration Improvements

**Original Priority:** High
**Estimated Effort:** 2-3 days
**Deferred Reason:** Large scope; synthesis can work without fancy orchestration initially

#### Problem Statement

Multiple issues with code review orchestration:

1. **Subagent output opaque** - Orchestrator runs specialists internally; parent sees only final summary; can't verify findings or debug issues

2. **Scanner context not visible** - Scanner runs but output not shown; can't verify hasUI, hasDatabase, etc.; debugging specialist selection difficult

3. **No progress indication** - Long-running reviews show no progress; user doesn't know if stuck or working; ~90 seconds of silence during --all runs

4. **Agent discovery unreliable** - 2 of 9 specialists missed without checklist; no automated discovery of all agents; manual orchestration error-prone

#### Proposed Solutions

**A. Intermediate Artifact Saving**
```
.claude/cache/
├── codebase-context.json       # Scanner output (already exists)
├── last-review/
│   ├── scanner-output.json     # What scanner detected
│   ├── specialists/
│   │   ├── security.json       # Each specialist's raw findings
│   │   ├── testing.json
│   │   └── ...
│   └── synthesis.json          # Pre-merge findings
```

**B. Progress Output Protocol**
```markdown
🔍 Phase 1: Scanning codebase...
   ✓ Detected: hasUI=true, hasDatabase=true, hasTypeScript=true

📋 Phase 2: Selecting specialists (7 of 9)...
   ✓ security (always)
   ✓ testing (always)
   ...
   ✗ infrastructure (hasCI=false)

🔄 Phase 3: Running specialists...
   [1/7] security... ✓ (5 findings)
   [2/7] testing... ✓ (3 findings)
   ...

📊 Phase 4: Synthesizing...
   ✓ Combined 23 findings, deduplicated 2
   ✓ Grade: B (82/100)
```

**C. Automated Agent Discovery**
```bash
# In orchestrator, dynamically find all specialists
SPECIALISTS=$(ls .claude/agents/*-reviewer.md | grep -v code-reviewer.md)
for specialist in $SPECIALISTS; do
    # Extract agent contract and check applicability
    ...
done
```

#### Implementation Plan

1. Design intermediate artifact structure
2. Update codebase-scanner to save detailed output
3. Update each specialist to save raw findings
4. Update orchestrator with progress output protocol
5. Add automated agent discovery
6. Update synthesis-agent to read from artifacts
7. Implement --verbose flag fully
8. Test end-to-end with all 9 specialists

#### Acceptance Criteria

- [ ] Scanner output visible (or saved to file)
- [ ] Progress shown during execution
- [ ] All 9 specialists discovered automatically
- [ ] Intermediate artifacts available for debugging
- [ ] --verbose shows detailed selection reasoning

### FEAT-21: Remediation Tracking

**Original Priority:** Medium
**Estimated Effort:** 3-4 hours
**Deferred Reason:** Adds complexity; users can track manually in INDEX.md for now

#### Problem Statement

After running code review, users must manually track which issues they've fixed. No systematic way to mark issues resolved or track remediation progress.

#### Proposed Solution

**New command: `/mark-resolved`**

```bash
/mark-resolved SEC-H1 "Added security headers in hooks.server.ts"
```

**Behavior:**
1. Find the issue in latest audit report
2. Add "Resolved" status with date and note
3. Update INDEX.md with resolution

**Enhanced INDEX.md format:**
```markdown
| ID | Audit | Issue | Status | Resolution |
|----|-------|-------|--------|------------|
| SEC-H1 | #5 | Missing headers | ✅ Fixed | 2026-01-19: Added in hooks.server.ts |
| TEST-H1 | #5 | Low coverage | 🔄 In Progress | 66% achieved, targeting 80% |
| DB-H1 | #5 | Missing types | ⏳ Awaiting User | Needs database credentials |
```

**Status values:**
- ✅ Fixed (code change made)
- ✅ Verified (existing protection confirmed - was false positive)
- 🔄 In Progress
- ⏳ Awaiting User (needs credentials/access/decision)
- ⏸️ Awaiting Upstream (dependency update needed)
- ❌ Won't Fix (documented reason)

#### Implementation Plan

1. Create `.claude/commands/mark-resolved.md`
2. Define status values and transitions
3. Update INDEX.md template with status columns
4. Add command to update both audit file and INDEX.md
5. Test with various status transitions

### FEAT-23: Architecture-Aware Coverage Targets

**Original Priority:** Medium
**Estimated Effort:** 3-4 hours
**Deferred Reason:** Complex logic; let testing-reviewer mature first

#### Problem Statement

Single 80% coverage target ignores architecture realities:
- Services/utilities: Easy to test → Should target 85%+
- Components: Harder to test → Target 60%
- Routes: Need E2E → N/A for unit tests

#### Proposed Solution

**Differentiated targets by code category:**

| Category | Files Pattern | Unit Test Target | Notes |
|----------|--------------|------------------|-------|
| Services/Utils | `**/services/*.ts`, `**/utils/*.ts` | 85% | Pure functions, easy to mock |
| Stores | `**/*.svelte.ts`, `**/stores/*.ts` | 75% | State management |
| Repositories | `**/repositories/*.ts` | 75% | Database access, need mocking |
| Components | `**/*.svelte` (non-route) | 60% | UI components |
| Routes | `**/routes/**/*.svelte` | N/A | Use E2E tests instead |

**Ceiling detection:**
```bash
TOTAL_FILES=$(find src -name "*.ts" -o -name "*.svelte" | wc -l)
ROUTE_FILES=$(find src/routes -name "*.svelte" | wc -l)
UNIT_TESTABLE_PCT=$(( (TOTAL_FILES - ROUTE_FILES) * 100 / TOTAL_FILES ))
echo "Unit testable ceiling: $UNIT_TESTABLE_PCT%"
```

**New audit output format:**
```markdown
### Coverage Analysis

| Category | Target | Current | Status |
|----------|--------|---------|--------|
| Unit Testable Code | 85% | 87% | ✅ Pass |
| Component Code | 60% | 45% | ⚠️ Needs Work |
| Routes (use E2E) | N/A | 0% | ℹ️ Expected |
| **Overall** | 70% | 66% | ✅ Acceptable |

**Note:** Routes at 0% is expected - they require E2E tests.
```

#### Implementation Plan

1. Define category patterns for common frameworks (Next.js, SvelteKit, etc.)
2. Update testing-reviewer.md with differentiated analysis
3. Add ceiling calculation to avoid unrealistic targets
4. Update audit report format with per-category breakdown
5. Test on projects with different architectures

### FEAT-24: Linked Issues in INDEX.md

**Original Priority:** Low (included with synthesis)
**Estimated Effort:** 1 hour
**Deferred Reason:** Natural extension of FEAT-1; add after synthesis is stable

#### Problem Statement

Multiple findings often relate to the same root issue. For example:
- SEC-H1 (Security): Missing security headers
- SEC-M3 (Security): No CSP header
- INFRA-H1 (Infrastructure): Security headers not configured

Fixing one often fixes all, but this relationship isn't visible.

#### Proposed Solution

**Add "Related" column to INDEX.md:**
```markdown
| ID | Audit | Issue | Related | Status |
|----|-------|-------|---------|--------|
| SEC-H1 | #5 | Missing headers | SEC-M3, INFRA-H1 | ✅ Fixed |
| SEC-M3 | #5 | CSP header | → SEC-H1 | ✅ Fixed |
| INFRA-H1 | #5 | Security headers | → SEC-H1 | ✅ Fixed |
```

**Detection logic in synthesis-agent:**
- Same file affected
- Same area/concept (headers, auth, etc.)
- Overlapping recommendations

#### Implementation Plan

1. Add related issue detection to synthesis-agent.md
2. Update INDEX.md template with Related column
3. Use `→ {ID}` notation for "see primary"
4. Test with real audit data showing related issues

### FEAT-2: CHANGELOG Excerpt in Upgrade

**Original Priority:** Low (nice polish)
**Estimated Effort:** 2 hours
**Deferred Reason:** Users can read CHANGELOG.md; not essential

#### Problem Statement

After upgrade completes, users see version number but not what changed.

#### Proposed Solution

```bash
echo ""
echo "📋 What's New in v$NEW_VERSION:"
changelog_excerpt=$(extract_changelog_section "$NEW_VERSION" "CHANGELOG.md")
if [ -n "$changelog_excerpt" ]; then
  echo "$changelog_excerpt" | head -7 | sed 's/^/  /'
else
  echo "  See CHANGELOG.md for details"
fi
echo ""
echo "Full changelog: https://github.com/rexkirshner/ai-context-system/blob/main/CHANGELOG.md"
```

**Function in common-functions.sh:**
```bash
extract_changelog_section() {
  local version="$1"
  local changelog="$2"
  awk -v ver="$version" '
    /^## \[/ { if (found) exit; if (index($0, ver)) found=1; next }
    found && /^- / { if (count++ < 7) print }
  ' "$changelog"
}
```

## v5.3.0 Candidates (High Priority Deferred)

### ARCH-4: Code Review Orchestration Improvements

**Original Priority:** High
**Estimated Effort:** 2-3 days
**Deferred Reason:** Large scope; synthesis can work without fancy orchestration initially

#### Problem Statement

Multiple issues with code review orchestration:

1. **Subagent output opaque** - Orchestrator runs specialists internally; parent sees only final summary; can't verify findings or debug issues

2. **Scanner context not visible** - Scanner runs but output not shown; can't verify hasUI, hasDatabase, etc.; debugging specialist selection difficult

3. **No progress indication** - Long-running reviews show no progress; user doesn't know if stuck or working; ~90 seconds of silence during --all runs

4. **Agent discovery unreliable** - 2 of 9 specialists missed without checklist; no automated discovery of all agents; manual orchestration error-prone

#### Proposed Solutions

**A. Intermediate Artifact Saving**
```
.claude/cache/
├── codebase-context.json       # Scanner output (already exists)
├── last-review/
│   ├── scanner-output.json     # What scanner detected
│   ├── specialists/
│   │   ├── security.json       # Each specialist's raw findings
│   │   ├── testing.json
│   │   └── ...
│   └── synthesis.json          # Pre-merge findings
```

**B. Progress Output Protocol**
```markdown
🔍 Phase 1: Scanning codebase...
   ✓ Detected: hasUI=true, hasDatabase=true, hasTypeScript=true

📋 Phase 2: Selecting specialists (7 of 9)...
   ✓ security (always)
   ✓ testing (always)
   ...
   ✗ infrastructure (hasCI=false)

🔄 Phase 3: Running specialists...
   [1/7] security... ✓ (5 findings)
   [2/7] testing... ✓ (3 findings)
   ...

📊 Phase 4: Synthesizing...
   ✓ Combined 23 findings, deduplicated 2
   ✓ Grade: B (82/100)
```

**C. Automated Agent Discovery**
```bash
# In orchestrator, dynamically find all specialists
SPECIALISTS=$(ls .claude/agents/*-reviewer.md | grep -v code-reviewer.md)
for specialist in $SPECIALISTS; do
    # Extract agent contract and check applicability
    ...
done
```

#### Implementation Plan

1. Design intermediate artifact structure
2. Update codebase-scanner to save detailed output
3. Update each specialist to save raw findings
4. Update orchestrator with progress output protocol
5. Add automated agent discovery
6. Update synthesis-agent to read from artifacts
7. Implement --verbose flag fully
8. Test end-to-end with all 9 specialists

#### Acceptance Criteria

- [ ] Scanner output visible (or saved to file)
- [ ] Progress shown during execution
- [ ] All 9 specialists discovered automatically
- [ ] Intermediate artifacts available for debugging
- [ ] --verbose shows detailed selection reasoning

### FEAT-21: Remediation Tracking

**Original Priority:** Medium
**Estimated Effort:** 3-4 hours
**Deferred Reason:** Adds complexity; users can track manually in INDEX.md for now

#### Problem Statement

After running code review, users must manually track which issues they've fixed. No systematic way to mark issues resolved or track remediation progress.

#### Proposed Solution

**New command: `/mark-resolved`**

```bash
/mark-resolved SEC-H1 "Added security headers in hooks.server.ts"
```

**Behavior:**
1. Find the issue in latest audit report
2. Add "Resolved" status with date and note
3. Update INDEX.md with resolution

**Enhanced INDEX.md format:**
```markdown
| ID | Audit | Issue | Status | Resolution |
|----|-------|-------|--------|------------|
| SEC-H1 | #5 | Missing headers | ✅ Fixed | 2026-01-19: Added in hooks.server.ts |
| TEST-H1 | #5 | Low coverage | 🔄 In Progress | 66% achieved, targeting 80% |
| DB-H1 | #5 | Missing types | ⏳ Awaiting User | Needs database credentials |
```

**Status values:**
- ✅ Fixed (code change made)
- ✅ Verified (existing protection confirmed - was false positive)
- 🔄 In Progress
- ⏳ Awaiting User (needs credentials/access/decision)
- ⏸️ Awaiting Upstream (dependency update needed)
- ❌ Won't Fix (documented reason)

#### Implementation Plan

1. Create `.claude/commands/mark-resolved.md`
2. Define status values and transitions
3. Update INDEX.md template with status columns
4. Add command to update both audit file and INDEX.md
5. Test with various status transitions

### FEAT-23: Architecture-Aware Coverage Targets

**Original Priority:** Medium
**Estimated Effort:** 3-4 hours
**Deferred Reason:** Complex logic; let testing-reviewer mature first

#### Problem Statement

Single 80% coverage target ignores architecture realities:
- Services/utilities: Easy to test → Should target 85%+
- Components: Harder to test → Target 60%
- Routes: Need E2E → N/A for unit tests

#### Proposed Solution

**Differentiated targets by code category:**

| Category | Files Pattern | Unit Test Target | Notes |
|----------|--------------|------------------|-------|
| Services/Utils | `**/services/*.ts`, `**/utils/*.ts` | 85% | Pure functions, easy to mock |
| Stores | `**/*.svelte.ts`, `**/stores/*.ts` | 75% | State management |
| Repositories | `**/repositories/*.ts` | 75% | Database access, need mocking |
| Components | `**/*.svelte` (non-route) | 60% | UI components |
| Routes | `**/routes/**/*.svelte` | N/A | Use E2E tests instead |

**Ceiling detection:**
```bash
TOTAL_FILES=$(find src -name "*.ts" -o -name "*.svelte" | wc -l)
ROUTE_FILES=$(find src/routes -name "*.svelte" | wc -l)
UNIT_TESTABLE_PCT=$(( (TOTAL_FILES - ROUTE_FILES) * 100 / TOTAL_FILES ))
echo "Unit testable ceiling: $UNIT_TESTABLE_PCT%"
```

**New audit output format:**
```markdown
### Coverage Analysis

| Category | Target | Current | Status |
|----------|--------|---------|--------|
| Unit Testable Code | 85% | 87% | ✅ Pass |
| Component Code | 60% | 45% | ⚠️ Needs Work |
| Routes (use E2E) | N/A | 0% | ℹ️ Expected |
| **Overall** | 70% | 66% | ✅ Acceptable |

**Note:** Routes at 0% is expected - they require E2E tests.
```

#### Implementation Plan

1. Define category patterns for common frameworks (Next.js, SvelteKit, etc.)
2. Update testing-reviewer.md with differentiated analysis
3. Add ceiling calculation to avoid unrealistic targets
4. Update audit report format with per-category breakdown
5. Test on projects with different architectures

### FEAT-24: Linked Issues in INDEX.md

**Original Priority:** Low (included with synthesis)
**Estimated Effort:** 1 hour
**Deferred Reason:** Natural extension of FEAT-1; add after synthesis is stable

#### Problem Statement

Multiple findings often relate to the same root issue. For example:
- SEC-H1 (Security): Missing security headers
- SEC-M3 (Security): No CSP header
- INFRA-H1 (Infrastructure): Security headers not configured

Fixing one often fixes all, but this relationship isn't visible.

#### Proposed Solution

**Add "Related" column to INDEX.md:**
```markdown
| ID | Audit | Issue | Related | Status |
|----|-------|-------|---------|--------|
| SEC-H1 | #5 | Missing headers | SEC-M3, INFRA-H1 | ✅ Fixed |
| SEC-M3 | #5 | CSP header | → SEC-H1 | ✅ Fixed |
| INFRA-H1 | #5 | Security headers | → SEC-H1 | ✅ Fixed |
```

**Detection logic in synthesis-agent:**
- Same file affected
- Same area/concept (headers, auth, etc.)
- Overlapping recommendations

#### Implementation Plan

1. Add related issue detection to synthesis-agent.md
2. Update INDEX.md template with Related column
3. Use `→ {ID}` notation for "see primary"
4. Test with real audit data showing related issues

### FEAT-9: Command File Refactoring

**Original Priority:** Medium (internal quality)
**Estimated Effort:** 4-6 hours
**Deferred Reason:** Users don't see this; do incrementally when already editing files

#### Problem Statement

Command files `init-context.md` and `save-full.md` are ~1000 lines each, mixing:
- Instructions
- Bash scripts
- Rationale/explanations
- Edge case handling

This makes them hard to follow and maintain.

#### Proposed Solution

**New structure:**
```
.claude/commands/
├── init-context.md           # Concise action checklist (<200 lines)
├── save-full.md              # Concise action checklist (<200 lines)
└── ...

.claude/docs/
├── init-context-reference.md # Detailed rationale, edge cases
├── save-full-reference.md    # Detailed rationale, edge cases
└── ...

scripts/
├── init-context-helper.sh    # Reusable bash functions
├── save-full-helper.sh       # Already exists, may need updates
└── ...
```

**Benefits:**
- Action files are scannable and executable
- Reference docs provide depth when needed
- Helper scripts are testable and reusable

#### Implementation Plan

1. Audit init-context.md and save-full.md structure
2. Identify what can be extracted to reference docs
3. Identify bash functions to extract to scripts
4. Refactor init-context.md (<300 lines)
5. Refactor save-full.md (<300 lines)
6. Update cross-references
7. Test both commands end-to-end

### FEAT-2: CHANGELOG Excerpt in Upgrade

**Original Priority:** Low (nice polish)
**Estimated Effort:** 2 hours
**Deferred Reason:** Users can read CHANGELOG.md; not essential

#### Problem Statement

After upgrade completes, users see version number but not what changed.

#### Proposed Solution

```bash
echo ""
echo "📋 What's New in v$NEW_VERSION:"
changelog_excerpt=$(extract_changelog_section "$NEW_VERSION" "CHANGELOG.md")
if [ -n "$changelog_excerpt" ]; then
  echo "$changelog_excerpt" | head -7 | sed 's/^/  /'
else
  echo "  See CHANGELOG.md for details"
fi
echo ""
echo "Full changelog: https://github.com/rexkirshner/ai-context-system/blob/main/CHANGELOG.md"
```

**Function in common-functions.sh:**
```bash
extract_changelog_section() {
  local version="$1"
  local changelog="$2"
  awk -v ver="$version" '
    /^## \[/ { if (found) exit; if (index($0, ver)) found=1; next }
    found && /^- / { if (count++ < 7) print }
  ' "$changelog"
}
```

## Ideas for Future Consideration

These are observations and ideas that may become features in future versions.

### Idea: Automated Code Review Scheduling

Run code review automatically on:
- Git pre-push hook
- CI/CD pipeline
- Weekly schedule

**Note:** May be complex to implement without CI integration.

### Idea: Issue Priority Scoring

Beyond severity, calculate priority based on:
- File change frequency (hot files = higher priority)
- User-facing impact
- Dependencies affected
- Fix effort

### Idea: Team Analytics Dashboard

Track across multiple code reviews:
- Trend lines for grade over time
- Most common issue categories
- Coverage improvement progress
- Remediation velocity

**Note:** Would require persistent storage and possibly a web UI.

### Idea: AI-Assisted Remediation

For certain finding types, offer to generate fix:
```
Would you like me to fix SEC-H1? [y/n]
> y

Adding security headers to hooks.server.ts...
✓ Fix applied. Please verify and commit.
```

**Note:** Risk of incorrect fixes; would need careful scoping.

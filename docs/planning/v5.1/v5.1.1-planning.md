## Bug Analysis

### BUG-A: grep Pattern Fails on macOS (CRITICAL)

**Source:** Video Gallery feedback
**Severity:** 🔴 Critical - Breaks auto-detection for all macOS users
**Location:** `scripts/common-functions.sh:2194`

**Problem:**
The `detect_project_description()` function uses Basic Regular Expression (BRE) alternation that fails silently on macOS BSD grep:

```bash
# Current (BROKEN on macOS BSD grep 2.6.0)
desc=$(grep -v '^#\|^$\|^==\|^--' "$readme" 2>/dev/null | head -1 | cut -c1-200)
```

**Root Cause:**
- BRE alternation (`\|`) combined with patterns like `^==` and `^--` causes BSD grep to fail silently
- `grep -v '^#\|^$'` works, but adding `\|^==` breaks it
- GNU grep (Linux) handles this correctly

**Tested Results (from feedback):**
```bash
grep -v '^#\|^$'           # WORKS on both
grep -v '^#\|^$\|^=='      # FAILS on macOS (returns empty)
grep -vE '^#|^$|^==|^--'   # WORKS on both (Extended regex)
```

**Fix:**
```bash
# Line 2194: Change -v to -vE (Extended Regular Expression)
desc=$(grep -vE '^#|^$|^==|^--' "$readme" 2>/dev/null | head -1 | cut -c1-200)
```

**Acceptance Criteria:**
1. Run on macOS: `source scripts/common-functions.sh && detect_project_description` returns description from README.md
2. Run on Linux: Same test passes
3. Test with README containing headers, blank lines, and `===` underlines

**Test Script:**
```bash
#!/bin/bash
# test-bug-a.sh - Test grep pattern compatibility

source scripts/common-functions.sh

# Create test README
cat > /tmp/test-readme.md << 'EOF'
# Project Title
================

A modern video gallery application for browsing and managing videos.

## Features
EOF

cd /tmp
desc=$(detect_project_description)
if [ "$desc" = "A modern video gallery application for browsing and managing videos." ]; then
  echo "✅ PASS: detect_project_description works"
  exit 0
else
  echo "❌ FAIL: Got '$desc'"
  exit 1
fi
```

### BUG-B: Parent Directory Detection Reports Siblings (MODERATE)

**Source:** Video Gallery feedback
**Severity:** 🟡 Moderate - Confusing warning, doesn't block installation
**Location:** `init-context.md:157`, `migrate-context.md:165`

**Problem:**
The parent `.claude` directory check uses `find` which searches siblings instead of ancestors:

```bash
# Current (searches siblings, not ancestors)
PARENT_CLAUDE=$(find "$CURRENT_DIR/.." -maxdepth 2 -name ".claude" 2>/dev/null | grep -v "$CURRENT_DIR/.claude" || echo "")
```

**Root Cause:**
- `find "$CURRENT_DIR/.."` searches the parent directory AND all its children
- With `-maxdepth 2`, it finds sibling project directories
- The grep exclusion doesn't work correctly for the current directory path

**Example:**
```
~/coding/
├── project-a/          # User runs /init-context here
│   └── .claude/
├── project-b/
│   └── .claude/        # FALSE POSITIVE: reported as "parent conflict"
└── project-c/
    └── .claude/        # FALSE POSITIVE: reported as "parent conflict"
```

**Fix:**
Replace the find command with an ancestor-walking approach:

```bash
# Walk up the directory tree checking only ancestors
check_parent_claude() {
  local current="$1"
  local parent

  # Walk up to 3 levels
  for i in 1 2 3; do
    parent=$(dirname "$current")
    if [ "$parent" = "$current" ]; then
      # Reached root
      return 1
    fi
    if [ -d "$parent/.claude" ]; then
      echo "$parent/.claude"
      return 0
    fi
    current="$parent"
  done

  return 1
}

PARENT_CLAUDE=$(check_parent_claude "$CURRENT_DIR")
```

**Acceptance Criteria:**
1. Running `/init-context` in `~/coding/project-a/` does NOT warn about `~/coding/project-b/.claude`
2. Running `/init-context` in `~/coding/project-a/` DOES warn about `~/coding/.claude` (if exists)
3. Running `/init-context` in `~/coding/project-a/src/` detects `~/coding/project-a/.claude` as parent

**Test Script:**
```bash
#!/bin/bash
# test-bug-b.sh - Test parent directory detection

# Setup
mkdir -p /tmp/test-parent/project-a/src
mkdir -p /tmp/test-parent/project-b/.claude
mkdir -p /tmp/test-parent/.claude  # Actual parent

cd /tmp/test-parent/project-a

# Source the function (after fix applied)
check_parent_claude() {
  local current="$1"
  local parent
  for i in 1 2 3; do
    parent=$(dirname "$current")
    [ "$parent" = "$current" ] && return 1
    [ -d "$parent/.claude" ] && { echo "$parent/.claude"; return 0; }
    current="$parent"
  done
  return 1
}

# Test 1: Should find /tmp/test-parent/.claude (ancestor)
result=$(check_parent_claude "$(pwd)")
if [ "$result" = "/tmp/test-parent/.claude" ]; then
  echo "✅ PASS: Found correct parent .claude"
else
  echo "❌ FAIL: Got '$result', expected '/tmp/test-parent/.claude'"
  exit 1
fi

# Test 2: Should NOT find sibling project-b/.claude
if echo "$result" | grep -q "project-b"; then
  echo "❌ FAIL: Incorrectly found sibling project"
  exit 1
else
  echo "✅ PASS: Did not find sibling project"
fi

# Cleanup
rm -rf /tmp/test-parent
echo "✅ All parent detection tests passed"
```

### BUG-C: Debug Output in generate_session_index (MINOR)

**Source:** Video Gallery feedback
**Severity:** 🟢 Minor - Cosmetic issue
**Location:** `scripts/common-functions.sh:3939-3944`

**Problem:**
The `generate_session_index()` function outputs debug information to stdout:
```
line_num=123
context_lines=$'...'
Session Index updated
```

**Root Cause:**
Variable assignments with `local` keyword may echo values in certain shell configurations, or there's residual debug output from development.

**Investigation Required:**
1. Check if `set -x` is enabled somewhere in the call chain
2. Check if the variable assignments are echoing due to shell quirks
3. Add explicit output suppression

**Fix:**
Ensure all variable assignments are silent and redirect any potential debug output:

```bash
# Line 3938-3944: Suppress any output from assignments
local line_num
line_num=$(grep -n "^## Session $session_num " "$sessions_file" 2>/dev/null | head -1 | cut -d: -f1) || true

if [ -n "$line_num" ]; then
  local context_lines
  context_lines=$(sed -n "$((line_num+1)),$((line_num+5))p" "$sessions_file" 2>/dev/null) || true
```

**Alternative Fix (if shell quirk):**
Add explicit silence around the assignments:

```bash
{
  local line_num
  line_num=$(grep -n "^## Session $session_num " "$sessions_file" | head -1 | cut -d: -f1)
} 2>/dev/null
```

**Acceptance Criteria:**
1. Running `/save-full` produces no `line_num=` or `context_lines=` output
2. Session Index is still correctly generated
3. Error messages (if any) still appear for actual errors

### BUG-D: Shell Arithmetic Errors from grep Newlines (MINOR)

**Source:** Video Gallery feedback
**Severity:** 🟢 Minor - Doesn't affect functionality
**Location:** Various arithmetic comparisons using grep output

**Problem:**
Error messages like `integer expression expected: 0\n0` appear when grep output contains newlines and is used in arithmetic comparisons.

**Root Cause:**
Some grep commands return multiline output that gets passed directly to `[ $var -gt 0 ]` comparisons.

**Example of problematic pattern:**
```bash
count=$(grep -c "pattern" file)  # May return "2\n" or "2\n0" on some systems
if [ "$count" -gt 0 ]; then      # Fails: "integer expression expected"
```

**Fix:**
Sanitize grep output before arithmetic comparison:

```bash
# Option 1: Use tr to remove newlines
count=$(grep -c "pattern" file | tr -d '\n')

# Option 2: Use head -1 to get first line only
count=$(grep -c "pattern" file | head -1)

# Option 3: Use arithmetic expansion which handles this better
count=$(grep -c "pattern" file || echo 0)
if (( count > 0 )); then
```

**Investigation Required:**
1. Grep for all arithmetic comparisons in common-functions.sh
2. Identify which ones use grep/wc output
3. Add sanitization to each

**Search Pattern:**
```bash
grep -n '\-gt\|\-lt\|\-eq\|\-ge\|\-le' scripts/common-functions.sh
```

**Acceptance Criteria:**
1. No "integer expression expected" errors during `/save-full` or `/init-context`
2. All arithmetic comparisons handle edge cases (empty output, newlines)
3. Test on both bash and zsh

**Test Script:**
```bash
#!/bin/bash
# test-bug-d.sh - Test arithmetic comparisons

source scripts/common-functions.sh

# Test 1: grep -c with newlines shouldn't cause errors
count=$(echo -e "line1\nline2" | grep -c "line" | tr -d '\n')
if [ "$count" -gt 0 ] 2>/dev/null; then
  echo "✅ PASS: Arithmetic comparison works"
else
  echo "❌ FAIL: Arithmetic comparison failed"
  exit 1
fi

# Test 2: Empty grep output
count=$(echo "" | grep -c "nonexistent" 2>/dev/null | tr -d '\n')
count=${count:-0}
if [ "$count" -eq 0 ] 2>/dev/null; then
  echo "✅ PASS: Empty output handled"
else
  echo "❌ FAIL: Empty output not handled"
  exit 1
fi

echo "✅ All arithmetic tests passed"
```

## Planning Philosophy

This plan follows principles designed to produce maintainable, robust code:

### 1. Incremental Checkpoints Over Big Bangs

Each feature is broken into small, independently verifiable steps. A step is complete when:
- Its test(s) pass in isolation
- It doesn't break existing tests
- The code can be committed and the system remains functional

**Example:** Phase 4 (Decision-Aware Review) breaks down into:
- 4.1: DECISIONS.md parser (test: parses fixtures correctly)
- 4.2: Decision matcher algorithm (test: matches with defined accuracy)
- 4.3: Agent context injection (test: agents receive decisions)
- 4.4: End-to-end integration (test: intentional decisions are downgraded)

### 2. Build on Existing Foundations

The AI Context System already has mature infrastructure:

| Component | Location | Status |
|-----------|----------|--------|
| Test framework | `scripts/tests/test-helpers.sh` | ✅ Mature (60+ tests) |
| Common utilities | `scripts/common-functions.sh` | ✅ Mature (57KB) |
| Agent contracts | `.claude/schemas/agent-contract.json` | ✅ Defined |
| Config schema | `config/context-config-schema.json` | ✅ Comprehensive |
| Codebase scanner | `.claude/agents/codebase-scanner.md` | ✅ Working |

**Rule:** Extend existing infrastructure rather than creating parallel systems.

### 3. Verifiable Over Subjective

Each checkpoint must have an objective pass/fail criterion:

| ❌ Subjective | ✅ Verifiable |
|---------------|---------------|
| "Works correctly" | "Returns exit code 0 and output matches golden file" |
| "Handles edge cases" | "Test files in `test/fixtures/edge-cases/` all pass" |
| "Improves performance" | "Completes in <5s on 10,000-line test project" |

### 4. Graceful Degradation

Features should work without optional dependencies:
- Code review works without DECISIONS.md (just no decision matching)
- Synthesis works without deduplication enabled (returns raw findings)
- Monorepo detection fails gracefully to single-project mode

### 5. No Shortcuts

- No "TODO: handle this later" comments
- No hardcoded values that should be configurable
- No copy-paste code that should be extracted to functions
- Fix root causes, not symptoms

#### 0.1 DECISIONS.md Parser

**Problem:** Multiple phases need to read and understand DECISIONS.md (Phase 1 archiving, Phase 4 injection). No parser exists.

**Solution:** Add `parse_decisions()` to `common-functions.sh`.

**Implementation:**
```bash
# In common-functions.sh

# Parses DECISIONS.md and outputs JSON array of decisions
# Usage: parse_decisions "/path/to/DECISIONS.md"
# Output: [{"id":"D001","title":"...","status":"active|superseded","date":"...","content":"..."}]
parse_decisions() {
  local decisions_file="$1"

  # Validate input
  [ -f "$decisions_file" ] || { echo "[]"; return 0; }

  # Extract decision blocks using markdown heading pattern
  # Pattern: ## D### - Title
  # ...content until next ## or EOF

  awk '
    /^## D[0-9]+ - / {
      if (id) print_decision()
      match($0, /D[0-9]+/)
      id = substr($0, RSTART, RLENGTH)
      title = substr($0, RSTART + RLENGTH + 3)
      content = ""
      next
    }
    /^## / { if (id) print_decision(); id = "" }
    id { content = content "\n" $0 }
    END { if (id) print_decision() }

    function print_decision() {
      gsub(/"/, "\\\"", content)
      gsub(/\n/, "\\n", content)
      printf "{\"id\":\"%s\",\"title\":\"%s\",\"content\":\"%s\"}\n", id, title, content
    }
  ' "$decisions_file" | jq -s '.'
}
```

#### 0.2 Decision Matching Algorithm

**Problem:** Phase 4 needs to match findings to decisions. The algorithm must be well-defined, not ad-hoc.

**Solution:** Implement keyword-based similarity matching with configurable thresholds.

**Algorithm Definition:**

```markdown
## Similarity Calculation

Given:
- Finding F with keywords K_f = {k1, k2, ...}
- Decision D with keywords K_d = {k1, k2, ...}

Similarity = |K_f ∩ K_d| / |K_f ∪ K_d| (Jaccard similarity)

## Keyword Extraction

Extract keywords from text by:
1. Lowercase all text
2. Remove punctuation
3. Split on whitespace
4. Remove stopwords (the, a, an, is, are, etc.)
5. Apply stemming (testing → test, tests → test)

## Semantic Equivalence Table

Some phrases are semantically equivalent. These are configured in `.context-config.json`:

| Canonical Form | Equivalents |
|----------------|-------------|
| "no tests" | "skip testing", "no test framework", "manual testing only" |
| "no typescript" | "vanilla js", "plain javascript", "javascript only" |
| "no database" | "static site", "json files for data", "file-based storage" |

Before matching, replace equivalents with canonical forms.

## Match Threshold

Default: 0.4 (40% Jaccard similarity)
Configurable via: `codeReview.decisionMatching.threshold`

Why 40%? Lower than original 70% because:
- Decisions and findings use different vocabulary
- We want to catch matches, then let humans verify
- False positives (marking real issues as intentional) are worse than false negatives
```

**Implementation:**
```bash
# In common-functions.sh

# Calculates Jaccard similarity between two keyword sets
# Usage: jaccard_similarity "keyword1 keyword2" "keyword2 keyword3"
# Output: 0.50 (float between 0 and 1)
jaccard_similarity() {
  local set_a="$1"
  local set_b="$2"

  # Implementation using awk for portability
  echo "$set_a" "$set_b" | awk '
    BEGIN { split("the a an is are was were be been being", stop); for (i in stop) stopwords[stop[i]]=1 }
    {
      n = split($0, words)
      mid = 0
      for (i=1; i<=n; i++) {
        w = tolower(words[i])
        gsub(/[^a-z0-9]/, "", w)
        if (w && !stopwords[w]) {
          if (i <= NF/2) { a[w]=1 }
          else { b[w]=1 }
        }
      }
    }
    END {
      for (k in a) { union[k]=1; if (k in b) inter++ }
      for (k in b) { union[k]=1 }
      n_union = length(union)
      if (n_union == 0) print "0.00"
      else printf "%.2f\n", inter / n_union
    }
  '
}

# Matches a finding against all decisions, returns best match
# Usage: match_finding_to_decisions "finding text" "/path/to/DECISIONS.md"
# Output: {"matched":true,"decision_id":"D001","confidence":0.65} or {"matched":false}
match_finding_to_decisions() {
  local finding="$1"
  local decisions_file="$2"
  local threshold="${3:-0.40}"

  # Parse decisions
  local decisions
  decisions=$(parse_decisions "$decisions_file")

  # Find best match
  echo "$decisions" | jq -r '.[] | "\(.id)\t\(.title) \(.content)"' | while IFS=$'\t' read -r id text; do
    similarity=$(jaccard_similarity "$finding" "$text")
    echo "$id $similarity"
  done | sort -k2 -rn | head -1 | awk -v thresh="$threshold" '
    $2 >= thresh { printf "{\"matched\":true,\"decision_id\":\"%s\",\"confidence\":%s}\n", $1, $2; exit }
    END { if (NR == 0 || $2 < thresh) print "{\"matched\":false}" }
  '
}
```

#### 0.3 Finding Deduplication Utilities

**Problem:** Phase 5 needs to deduplicate findings. The algorithm must handle multiple dedup strategies.

**Solution:** Implement layered deduplication with clear rules.

**Deduplication Layers:**

```markdown
## Layer 1: Location-Based (Same file:line)

Findings at identical file:line are definitely duplicates.

Merge strategy:
- Combine into single finding
- Severity: Take highest (CRITICAL > HIGH > MEDIUM > LOW)
- Title: Use most descriptive (longest)
- Detecting agents: List all
- Recommendations: Merge unique recommendations

## Layer 2: Pattern-Based (Same issue type across files)

Findings with same `category` + similar `title` across different files may be grouped.

Examples:
- "Missing error handling in auth.ts:45" + "Missing error handling in db.ts:23"
  → Group as "Missing error handling (2 files)"

Grouping threshold: 3+ similar findings triggers grouping
Output: Original findings remain, but grouped finding added with cross-references

## Layer 3: Semantic Deduplication (Different words, same issue)

NOT implemented in v5.1.0 - requires NLP, out of scope.
Listed here to document what we're NOT doing.
```

**Implementation:**
```bash
# In common-functions.sh

# Deduplicates findings by location
# Input: JSON array of findings (stdin or file)
# Output: JSON array of deduplicated findings
dedupe_by_location() {
  jq '
    group_by(.location.file + ":" + (.location.line | tostring))
    | map(
      if length == 1 then .[0]
      else
        .[0] + {
          "id": (.[0].id + "-MERGED"),
          "severity": ([.[] | .severity] | map(
            if . == "CRITICAL" then 4
            elif . == "HIGH" then 3
            elif . == "MEDIUM" then 2
            else 1 end
          ) | max | if . == 4 then "CRITICAL" elif . == 3 then "HIGH" elif . == 2 then "MEDIUM" else "LOW" end),
          "detectedBy": [.[] | .id | split("-")[0]] | unique,
          "mergedFrom": [.[] | .id]
        }
      end
    )
  '
}

# Groups similar findings across files
# Input: JSON array of findings (stdin or file)
# Output: JSON array with groupings added
group_similar_findings() {
  local min_group_size="${1:-3}"

  jq --argjson min "$min_group_size" '
    # Group by category + title pattern
    group_by(.category + ":" + (.title | gsub(" in .*$"; "")))
    | map(
      if length >= $min then
        . + [{
          "id": "GROUP-" + (.[0].category) + "-" + (length | tostring),
          "type": "group",
          "pattern": (.[0].title | gsub(" in .*$"; "")),
          "count": length,
          "files": [.[] | .location.file] | unique,
          "memberIds": [.[] | .id]
        }]
      else .
      end
    )
    | flatten
  '
}
```

# In common-functions.sh

# Detects monorepo type and returns configuration
# Usage: detect_monorepo [directory]
# Output: JSON object with type, workspaces, commands
detect_monorepo() {
  local dir="${1:-.}"

  # Check indicators in priority order
  if [ -f "$dir/turbo.json" ]; then
    echo '{"type":"turborepo","buildCmd":"turbo build","workspaceCmd":"turbo build --filter="}'
  elif [ -f "$dir/nx.json" ]; then
    echo '{"type":"nx","buildCmd":"nx run-many --target=build","workspaceCmd":"nx run --project="}'
  elif [ -f "$dir/lerna.json" ]; then
    echo '{"type":"lerna","buildCmd":"lerna run build","workspaceCmd":"lerna run build --scope="}'
  elif [ -f "$dir/pnpm-workspace.yaml" ]; then
    echo '{"type":"pnpm","buildCmd":"pnpm -r build","workspaceCmd":"pnpm --filter="}'
  elif [ -f "$dir/package.json" ] && jq -e '.workspaces' "$dir/package.json" >/dev/null 2>&1; then
    # Yarn or npm workspaces - check for yarn.lock
    if [ -f "$dir/yarn.lock" ]; then
      echo '{"type":"yarn","buildCmd":"yarn workspaces run build","workspaceCmd":"yarn workspace "}'
    else
      echo '{"type":"npm","buildCmd":"npm run build --workspaces","workspaceCmd":"npm run build -w "}'
    fi
  else
    echo '{"type":"single","buildCmd":"npm run build","workspaceCmd":null}'
  fi
}

# Lists all workspaces in a monorepo
# Usage: list_workspaces [directory]
# Output: JSON array of workspace objects
list_workspaces() {
  local dir="${1:-.}"
  local mono_type
  mono_type=$(detect_monorepo "$dir" | jq -r '.type')

  case "$mono_type" in
    turborepo|nx)
      # Find all package.json files excluding node_modules
      find "$dir" -name "package.json" -not -path "*/node_modules/*" -exec dirname {} \; \
        | while read -r ws; do
            name=$(jq -r '.name // "unnamed"' "$ws/package.json")
            echo "{\"name\":\"$name\",\"path\":\"$ws\"}"
          done | jq -s '.'
      ;;
    pnpm)
      # Parse pnpm-workspace.yaml
      yq -o=json '.packages[]' "$dir/pnpm-workspace.yaml" 2>/dev/null \
        | xargs -I{} find "$dir" -path "*{}*/package.json" -exec dirname {} \; \
        | while read -r ws; do
            name=$(jq -r '.name // "unnamed"' "$ws/package.json")
            echo "{\"name\":\"$name\",\"path\":\"$ws\"}"
          done | jq -s '.'
      ;;
    yarn|npm)
      # Parse package.json workspaces
      jq -r '.workspaces[]' "$dir/package.json" 2>/dev/null \
        | xargs -I{} find "$dir" -path "*{}*/package.json" -exec dirname {} \; \
        | while read -r ws; do
            name=$(jq -r '.name // "unnamed"' "$ws/package.json")
            echo "{\"name\":\"$name\",\"path\":\"$ws\"}"
          done | jq -s '.'
      ;;
    *)
      echo "[]"
      ;;
  esac
}
```

#### 7.2 Security-Relevant Pattern Improvements

**Problem:** Current filename patterns miss important files, but naive expansion creates noise.

**Noisy patterns to avoid:**
- `*key*` → matches `keyboard.ts`, `keydown.ts`, `hotkey.ts`
- `*api*` → matches `api/routes.ts` (just an API folder, not credentials)
- `*password*` → matches `password_policy.ts`, `password_validator.ts`

**Solution:** Two-tier detection with exclusions and content-based confirmation.

**Implementation:**
```markdown
## Security Pattern Detection (Enhanced)

### Tier 1: Filename Patterns (High Confidence)

Files with these patterns are always flagged:
- `*auth*.{js,ts,py,go,java}` - Authentication logic
- `*login*.{js,ts,py,go,java}` - Login handling
- `*session*.{js,ts,py,go,java}` - Session management
- `*.env*` - Environment files (but NOT .env.example)
- `*credential*.{js,ts,py,go,java}` - Credential handling
- `*oauth*.{js,ts,py,go,java}` - OAuth implementation
- `*jwt*.{js,ts,py,go,java}` - JWT handling

### Tier 2: Filename Patterns with Exclusions (Medium Confidence)

These patterns are flagged UNLESS they match an exclusion:

| Pattern | Exclusions |
|---------|------------|
| `*secret*` | `*_test*`, `*_spec*`, `*.md` |
| `*token*` | `*tokenize*`, `*token_type*` |
| `*password*` | `*_policy*`, `*_validator*`, `*_strength*`, `*_rules*` |
| `*key*` | `*keyboard*`, `*keydown*`, `*keyup*`, `*keypress*`, `*hotkey*`, `*keyframe*` |
| `*api*` | Directories (only flag files with api in name, not api/file.ts) |

### Tier 3: Content-Based Confirmation (for ambiguous files)

If filename is ambiguous, scan first 100 lines for:
- Hardcoded strings that look like secrets: `["'][\w]{20,}["']`
- API key patterns: `(api[_-]?key|apikey)\s*[:=]`
- Password assignment: `password\s*[:=]\s*["']`
- Connection strings: `(mongodb|postgres|mysql):\/\/`

Only flag if content patterns match.

### Configuration

Users can customize in .context-config.json:
```json
{
  "scanner": {
    "securityPatterns": {
      "additionalPatterns": ["*stripe*", "*payment*"],
      "exclusions": ["*mock*", "*stub*", "*fixture*"]
    }
  }
}
```
```

5. `api/routes.ts` → NOT flagged (directory, not file pattern)

## Risks

| Phase | Risk | Likelihood | Impact | Mitigation |
|-------|------|------------|--------|------------|
| 0.2 | Jaccard similarity not suitable for all text | Medium | Medium | Configurable threshold, fallback to keyword exact match |
| 4 | Decision matching too aggressive (hides real issues) | Medium | High | Start with 40% threshold (not 70%), log all matches for review |
| 4 | Decision matching too weak (still flags intentional) | Medium | Low | Allow custom patterns in config, semantic equivalence table |
| 5 | Deduplication merges unrelated findings | Low | Medium | Only merge same file:line, pattern grouping is additive |
| 5 | Report generation fails mid-process | Low | Medium | Atomic writes via temp file, recovery cleans up .tmp files |
| 6 | Monorepo detection false positives | Low | Low | Priority order for indicators, graceful fallback to single |
| 7 | Security patterns too noisy (keyboard.ts flagged) | Medium | Low | Three-tier system with exclusions, content-based confirmation |
| 9 | .context-local/ conflicts with .claude/ | Low | Medium | Clear precedence rules, warning on conflicts |
| 1 | Archive loses important decisions | Low | High | Require user confirmation, keep recent 50 |

**Risk Summary:**
- **Highest risk:** Phase 4 (decision matching logic is complex, requires tuning)
- **Medium risk:** Phase 0.2, 7 (new algorithms that may need adjustment)
- **Lowest risk:** Phase 2, 8 (documentation/already done)

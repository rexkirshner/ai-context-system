# v5.1.0 Planning: Context System Refinements

**Created:** 2026-01-14
**Updated:** 2026-01-15 (restructured with priorities, decisions, testing/rollback plans)
**Status:** Planning
**Baseline:** v5.0.2 (starting point for this release)
**Target:** Next minor release after v5.0.2 stabilizes

---

## Executive Summary

v5.1.0 focuses on two themes:

**Theme 1: Right-Sizing** - Ensuring each file serves its purpose without becoming unwieldy.
**Theme 2: Code Review Intelligence** - Making the agent-based code review system smarter.

### Phase Overview

| Phase | Theme | Focus | Priority | Complexity | Status |
|-------|-------|-------|----------|------------|--------|
| 1 | Right-Sizing | File growth management | Medium | Simple | Planned |
| 2 | Right-Sizing | File purpose clarity | Low | Simple | Planned |
| 3 | Right-Sizing | Efficiency improvements | Medium | Medium | Planned |
| 4 | Code Review | Context-aware agents | **High** | Complex | Planned |
| 5 | Code Review | Automated synthesis | **High** | Complex | Planned |
| 6 | Code Review | Monorepo support | Medium | Medium | Planned |
| 7 | Code Review | Scanner improvements | Low | Simple | Planned |
| 8 | Code Review | Cost optimization | Medium | Medium | ✅ Done |

**Priority rationale:**
- **High (4, 5):** Directly addresses most common user complaints (false positives, manual dedup)
- **Medium (1, 3, 6, 8):** Meaningful improvements, not blocking adoption
- **Low (2, 7):** Nice-to-have, documentation/polish

**Recommended execution order:** 4 → 5 → 1 → 6 → 3 → 7 → 2 (Phase 8 already done)

---

## Non-Goals (Out of Scope for v5.1.0)

The following are explicitly **not** planned for this release:

1. **New context file types** - Not adding new required files (already have enough)
2. **Breaking file format changes** - All existing context files remain compatible
3. **Multi-language support** - Keeping English-only for now
4. **GUI/web interface** - Remains CLI-focused
5. **Real-time collaboration** - No live sync between AI sessions
6. **Automated code fixes** - Agents report only, don't modify code
7. **Integration with external tools** - No Jira, Linear, GitHub Issues sync
8. **Custom agent creation** - Users can't define their own review agents yet

These may be considered for v5.2.0 or later based on demand.

## Feedback Summary

### What's Working Well

**Context System:**
- STATUS.md design (dashboard at top, scannable)
- Layered approach (quick scan → deep dive)
- Separation of concerns (decisions vs sessions vs status)

**Code Review (v5.0.0+):**
- Parallel execution of 9 specialist agents
- Agent discovery and contract parsing
- Cache validity detection
- Individual agent finding quality
- Structured audit output format

### What Needs Improvement

**Context System:**
- File growth is unmanaged (DECISIONS.md, SESSIONS.md grow forever)
- No "lite" mode for quick context loading
- Too many files (7-11) can overwhelm
- Unclear what's "core" vs "optional"
- ARCHITECTURE.md becomes book-length in complex projects

**Code Review:**
- Agents unaware of DECISIONS.md (flag intentional decisions as issues)
- Manual synthesis and deduplication (~136 → ~45 findings)
- Manual report generation (no auto-creation of audit files)
- False positives (e.g., ".env committed" when it's not)
- Codebase scanner incomplete (linesScanned: 0, missing security patterns)
- No dry-run mode to preview agent selection
- Monorepo structures not detected

### Phase 4: Context-Aware Code Review Agents

**Source:** v5.0.1 production feedback - Agents flag intentional decisions as issues

#### 4.1 DECISIONS.md Context Injection

**Problem:** Code review agents flag intentional decisions as issues. Example: Testing agent flags "No test framework" as CRITICAL, but it's a documented intentional decision for a portfolio project.

**Solution:** Inject DECISIONS.md context into each specialist agent before review.

**Implementation:**
```markdown
## Code Reviewer Orchestrator Changes

### Step 2.5: Load Project Decisions (NEW)

Before invoking specialist agents, read DECISIONS.md and extract:
1. Intentional limitations (e.g., "No tests - portfolio project")
2. Technology choices (e.g., "Vanilla JS preferred over TypeScript")
3. Scope constraints (e.g., "No database - static site")

Pass this context to each agent as "Known Intentional Decisions" section.

### Agent Behavior Changes

When an agent finds an issue that matches a documented decision:
1. Downgrade severity (CRITICAL → LOW)
2. Add note: "Intentional per DECISIONS.md: D023"
3. Move to "Intentional Exceptions" section of report
```

**Verification Checkpoint:**
```bash

**Decision:** Skip test framework for portfolio project.
**Rationale:** Minimal complexity, static content." > context/DECISIONS.md

# Testing agent should NOT flag missing tests as CRITICAL
/code-review --domain testing

# Check output
grep -q "Intentional per DECISIONS.md" audit-output.md && echo "PASS" || echo "FAIL"
```

### Phase 5: Automated Synthesis and Reporting

**Source:** v5.0.1 production feedback - Manual deduplication and report generation

#### 5.1 Automated Finding Deduplication

**Problem:** Same issue flagged by multiple agents. Example:
- innerHTML usage flagged by Security, Accessibility, AND Performance
- Missing tests flagged by Testing AND TypeScript
- ~136 raw findings → ~45 after manual dedup

**Solution:** Automated deduplication in synthesis step.

**Implementation:**
```markdown
## Synthesis Agent Enhancement

### Deduplication Algorithm

1. Group findings by file path + line number
2. For findings at same location:
   - Merge into single finding
   - Combine severity (take highest)
   - List all detecting agents
   - Merge recommendations
3. Group similar findings by pattern:
   - "Missing X" patterns
   - "No Y configured" patterns
   - Same issue type in different files
4. Output deduplicated list with cross-references

### Example

Raw findings:
- SEC-001: innerHTML in PhotoGallery.astro:363
- A11Y-012: innerHTML in PhotoGallery.astro:363
- PERF-007: innerHTML in PhotoGallery.astro:363

Deduplicated:
- MERGED-001: innerHTML usage in PhotoGallery.astro:363
  - Detected by: Security, Accessibility, Performance
  - Severity: HIGH (from Security)
  - See also: SEC-001, A11Y-012, PERF-007
```

**Verification Checkpoint:**
```bash
# Input: 3 findings for same location
# Output: 1 merged finding with 3 agent references
findings_in=3
findings_out=$(jq '.findings | length' output.json)
[ "$findings_out" -eq 1 ] && echo "PASS: Deduplication works" || echo "FAIL"
```

**Files:**
- MOD: `.claude/agents/synthesis-agent.md` (add deduplication logic)

### Phase 6: Monorepo Support

**Source:** v5.0.1 production feedback - Codebase scanner misses dependencies in monorepos

#### 6.1 Monorepo Detection

**Problem:** Codebase scanner only checks root `package.json`, missing `apps/*/package.json`.

**Solution:** Detect and scan monorepo structures.

**Implementation:**
```markdown
## Codebase Scanner Enhancement

### Monorepo Detection

Check for monorepo indicators:
1. `pnpm-workspace.yaml` exists
2. `turbo.json` exists
3. `lerna.json` exists
4. `package.json` has `workspaces` field
5. `apps/` or `packages/` directories exist

### Workspace Scanning

If monorepo detected:
1. Find all `package.json` files
2. Aggregate dependencies across workspaces
3. Identify shared vs workspace-specific deps
4. Report structure in scan output

```json
{
  "structure": {

    "monorepoType": "turborepo",

      {"name": "api", "path": "apps/api", "type": "express"},
      {"name": "ui", "path": "packages/ui", "type": "library"}

  "dependencies": {
    "shared": ["react", "typescript"],

| 4 | Decision matching too weak (still flags intentional) | Medium | Low | Allow custom patterns in config |

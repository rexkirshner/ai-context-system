## Feature Analysis

### FEAT-1: Automated Code Review Synthesis (HIGH PRIORITY)

**Source:** NCL feedback (OBS-007, OBS-008)
**Priority:** High - Significant manual work currently required
**Effort:** Large (new command + synthesis logic)

**Problem:**
After parallel code review agents complete, users must manually:
1. Collect all 7+ agent outputs
2. Merge findings into single array
3. Deduplicate overlapping findings (DB + PERF may point to same issue)
4. Calculate severity counts and overall grade
5. Generate JSON and Markdown reports

**Current State:**
```
/code-review --prelaunch
  → 7 agents run in parallel
  → Each outputs JSON findings
  → User manually combines and grades
```

**Proposed Solution:**
Add a `synthesis-agent.md` (already exists) that automatically:
1. Collects all agent outputs from a review session
2. Groups related findings by file/location
3. Identifies when multiple specialists found the same root cause
4. Creates "primary" finding with "related" references
5. Calculates weighted grade
6. Generates final report

**Implementation Options:**

**Option A: Post-hoc Synthesis Command**
```bash
/code-review-synthesize
# Reads: .claude/cache/review-session-*.json
# Outputs: docs/audits/audit-04.{md,json}
```

**Option B: Automatic Synthesis in Orchestrator**
```bash
/code-review --prelaunch
# Phase 1: Run specialists in parallel
# Phase 2: Automatically synthesize results
# Phase 3: Generate report
```

**Option C: Streaming Synthesis**
```bash
/code-review --prelaunch
# As each agent completes, feed to synthesis
# Show running grade/count
# Final report when all complete
```

**Recommendation:** Option B (Automatic in orchestrator) with Option A available for manual re-synthesis.

**Acceptance Criteria:**
1. Running `/code-review --prelaunch` produces a final report without manual intervention
2. Report includes: combined findings, deduplication notes, overall grade, recommendations
3. Related findings are grouped (e.g., "DB-001 and PERF-005 share root cause")
4. Grade calculation matches documented formula
5. JSON and Markdown reports generated to `docs/audits/`

**Test Cases:**
```bash
# Test 1: Full synthesis with all 8 specialists
/code-review --all
# Verify: Single combined report generated

# Test 2: Deduplication works
# Setup: Create findings that should dedupe
# Verify: Related findings grouped, not duplicated in count

# Test 3: Grade calculation
# Setup: Known severity distribution
# Verify: Grade matches expected value
```

### FEAT-4: Working Directory Detection for /update-context-system (MEDIUM PRIORITY)

**Source:** NCL feedback (OBS-003)
**Priority:** Medium - Friction in monorepo workflows
**Effort:** Small

**Problem:**
Running `/update-context-system` from a subdirectory fails:
```bash
cd ~/project/apps/web
/update-context-system
# Error: No context/.context-config.json found
```

Users must manually `cd` to project root.

**Current State:**
Other commands use `find-context-folder.sh` to auto-detect, but `/update-context-system` doesn't.

**Proposed Solution:**
Add context folder detection to `/update-context-system`:

```bash
# Step 0: Find context folder (same as other commands)
source "$(dirname "${BASH_SOURCE[0]}")/../scripts/find-context-folder.sh" || exit 1
CONTEXT_DIR=$(find_context_folder) || exit 1
PROJECT_ROOT=$(dirname "$CONTEXT_DIR")
cd "$PROJECT_ROOT"
```

**Acceptance Criteria:**
1. `/update-context-system` works from any subdirectory within project
2. Detects context folder up to 3 levels up
3. Clear error message if no context folder found
4. Backup and update happen in correct location

**Test Cases:**
```bash
# Test 1: Run from subdirectory
cd project/apps/web/src
/update-context-system
# Verify: Updates project root, not subdirectory

# Test 2: Run from unrelated directory
cd /tmp
/update-context-system
# Verify: Clear error "No context folder found"
```

### FEAT-6: Document Specialist Selection Logic (MEDIUM PRIORITY)

**Source:** NCL feedback (CONF-001)
**Priority:** Medium - Documentation gap
**Effort:** Small

**Problem:**
Users don't understand how specialists are selected:
- When does infrastructure-reviewer run?
- What does `hasCI: false` in scanner output mean?
- Do presets override applicability?

**Current State:**
Agent contracts contain `applicability` fields, but selection logic isn't documented.

**Proposed Solution:**
Add "Specialist Selection Logic" section to `/code-review` documentation:

```markdown
## Specialist Selection Logic

### Automatic Selection (no flags)
When running `/code-review` without flags, specialists are selected based on:

1. **Scanner Output** - `codebase-context.json` contains detected features
2. **Agent Applicability** - Each agent declares requirements

| Agent | Requires | Example |
|-------|----------|---------|
| security-reviewer | `always: true` | Always runs |
| database-reviewer | `hasDatabase: true` | Prisma/Drizzle detected |
| infrastructure-reviewer | `hasCI: true` | .github/workflows exists |
| testing-reviewer | `hasTests: true` | test/ or *.test.* files |

### Preset Behavior
Presets (`--prelaunch`, `--backend`, `--frontend`) include specific specialists:

| Preset | Specialists |
|--------|-------------|
| `--prelaunch` | security, performance, accessibility, seo |
| `--backend` | security, database, testing, typescript |
| `--frontend` | performance, accessibility, seo, typescript |
| `--all` | All 8 specialists |

**Note:** Presets override applicability. `--all` runs all specialists even if requirements aren't met.

### Manual Override
Explicit flags always run the specified specialist:
```bash
/code-review --infrastructure  # Runs even without CI detected
```
```

**Acceptance Criteria:**
1. Documentation explains automatic selection
2. All agent requirements documented
3. Preset behavior clarified
4. Manual override behavior explained

### FEAT-7: Progress Indicators for Long-Running Agents (LOW PRIORITY)

**Source:** NCL feedback (OBS-006)
**Priority:** Low - Nice to have
**Effort:** Medium

**Problem:**
Testing agent can take 90+ seconds on large codebases. No feedback during execution.

**Current State:**
```
Running testing-reviewer...
[silence for 90 seconds]
Results: ...
```

**Proposed Solution:**
Add progress streaming for agents that take >10 seconds:

```
Running testing-reviewer...
  Analyzing test files... (234 files)
  Checking coverage config...
  Scanning test patterns...
  Evaluating test quality...
Results: ...
```

**Implementation Options:**

**Option A: Timeout-based status**
If agent hasn't responded in 30s, show "Still analyzing..."

**Option B: Streaming progress**
Agents emit progress events that orchestrator displays

**Option C: Estimated time**
Show "Estimated time: ~60s for large codebases"

**Recommendation:** Option A (simplest, most robust)

**Acceptance Criteria:**
1. Operations >30s show "Still working..." message
2. Message updates every 30s
3. Final result still displays correctly
4. Doesn't interfere with agent output

## Technical Design: Code Review Synthesis

### Architecture

```
┌─────────────────┐     ┌─────────────────┐
│ security-       │     │ performance-    │
│ reviewer        │     │ reviewer        │
└────────┬────────┘     └────────┬────────┘
         │                       │
         ▼                       ▼
┌─────────────────────────────────────────┐
│         Synthesis Agent                  │
│  ┌─────────────────────────────────┐    │
│  │ 1. Collect all findings          │    │
│  │ 2. Group by file/location        │    │
│  │ 3. Identify shared root causes   │    │
│  │ 4. Deduplicate & reference       │    │
│  │ 5. Calculate grade               │    │
│  │ 6. Generate report               │    │
│  └─────────────────────────────────┘    │
└────────────────────┬────────────────────┘
                     │
                     ▼
         ┌───────────────────┐
         │ docs/audits/      │
         │   audit-04.md     │
         │   audit-04.json   │
         └───────────────────┘
```

### Deduplication Algorithm

```
For each finding F:
  1. Extract location (file, line range)
  2. Extract keywords (function names, patterns)
  3. Compare against all other findings:
     - Same file + overlapping lines = potential duplicate
     - Same function name = potential duplicate
     - Same root cause pattern = related
  4. Group duplicates under primary finding
  5. Add "Related" references to secondary findings
```

### Grade Calculation

```
Base Score = 100

Deductions:
  Critical finding: -25 points each
  High finding:     -10 points each
  Medium finding:   -3 points each
  Low finding:      -1 point each

Grade Thresholds:
  A: 90-100
  B: 80-89
  C: 70-79
  D: 60-69
  F: <60
```

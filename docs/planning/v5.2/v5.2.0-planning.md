### 3.2 Add extract_changelog_section() Function

**Location:** `scripts/common-functions.sh`

```bash
# Extract changelog section for a specific version
# Usage: extract_changelog_section "5.1.0" "CHANGELOG.md"
# Returns: Bullet points for that version (max 7)
extract_changelog_section() {
  local version="$1"
  local changelog="$2"

  if [ ! -f "$changelog" ]; then
    return 1
  fi

  # Find version section and extract bullets
  awk -v ver="$version" '
    /^## \[/ { if (found) exit; if (index($0, ver)) found=1; next }
    found && /^- / { if (count++ < 7) print }
  ' "$changelog"
}
```

**Acceptance Criteria:**
- [ ] Function added to common-functions.sh
- [ ] Returns max 7 bullet points
- [ ] Returns empty if version not found

## ARCH-1: Shell State Persistence (Systemic Issue)

**Source:** All three projects - BUG-023, multiple reports
**Severity:** 🟡 Moderate - AI works around it, but documentation is misleading
**Affected Commands:** /update-context-system, /code-review, potentially others

### Problem Statement

Commands are written assuming a persistent shell where:
- Variables persist between commands (`export VAR=value`)
- Sourced functions remain available (`source scripts/common-functions.sh`)
- Exports affect subsequent commands

**Reality:** Claude Code's Bash tool creates isolated shells for each invocation. Each bash block runs in a fresh environment.

### Impact

1. Functions from `common-functions.sh` aren't available after sourcing
2. Variables set in Step N don't exist in Step N+1
3. `source` and `export` have no persistent effect
4. AI must work around by re-sourcing or inlining logic

### Proposed Solutions

**Option A: Document the Limitation** (Low effort, addresses confusion)
- Add clear note to all commands: "Each bash block runs in isolated shell"
- Provide inline implementations instead of function references
- Remove misleading `source` commands

**Option B: Make Each Step Self-Contained** (Medium effort, best practice)
- Each bash block sources required dependencies
- No cross-block variable dependencies
- Functions called where needed, not sourced once

**Option C: Single-Script Approach** (High effort, cleanest)
- Convert complex commands to single bash scripts
- Script runs atomically, state preserved within
- AI calls script instead of executing steps

### High-Level Plan

1. Audit all command files for shell state assumptions
2. Identify which approach fits each command
3. Refactor /update-context-system (most affected)
4. Refactor /code-review orchestration
5. Update documentation to match chosen approach
6. Add automated tests for isolated shell execution

### Acceptance Criteria

- [ ] No command assumes cross-block variable persistence
- [ ] All function usage either inlined or re-sourced
- [ ] Documentation clearly states execution model
- [ ] Commands work correctly when AI runs each block separately

## ARCH-2: SESSIONS.md Token Limit (Architectural)

**Source:** NCL project - BUG in /save-full
**Severity:** 🟡 Moderate - Defeats purpose of SESSIONS.md for AI continuity
**Threshold:** Files exceeding 25,000 tokens (Claude Code Read tool limit)

### Problem Statement

SESSIONS.md grows with each documented session (~60-80 lines per session). When file exceeds 25,000 tokens, AI cannot read it:

```
Error: File content (38020 tokens) exceeds maximum allowed tokens (25000).
Please use offset and limit parameters to read specific portions.
```

### Impact

1. **Session continuity breaks** - AI can't review recent sessions for context
2. **Mental Models lost** - Session Mental Models section specifically designed for AI continuity becomes inaccessible
3. **Workarounds fragile** - Using grep/offset loses context about format and patterns
4. **Scales poorly** - Every session adds content; problem only gets worse

### Proposed Solutions

**Recommended: Session Index + Rolling Archive**

```
context/
├── SESSIONS.md              # Session Index table + last 20-30 sessions
└── sessions-archive.md      # Older sessions (archived automatically)
```

**Session Index format:**
```markdown
## Session Index

| # | Date | Phase | Focus | Key Mental Models |
|---|------|-------|-------|-------------------|
| 50 | 2026-01-23 | Production | Member Onboarding | Password enforcement flow |
| 49 | 2026-01-22 | Production | Client Feedback | Turso architecture |
| ... | ... | ... | ... | ... |
```

**Archival rules:**
- Keep last 20-30 sessions in full detail in SESSIONS.md
- When session count exceeds 30, move oldest to sessions-archive.md
- /save-full manages rotation automatically
- Session Index always contains ALL sessions (for navigation)

### High-Level Plan

1. Design Session Index schema (columns, format)
2. Update SESSIONS.template.md with index section
3. Create sessions-archive.md template
4. Update /save-full to:
   - Add entry to Session Index
   - Check if rotation needed (>30 sessions)
   - Archive oldest sessions if needed
5. Update /review-context to read index first
6. Migrate existing large SESSIONS.md files
7. Document the system

### Acceptance Criteria

- [ ] SESSIONS.md stays under 20,000 tokens
- [ ] Session Index provides overview of all sessions
- [ ] Archived sessions still grep-able
- [ ] /save-full manages rotation automatically
- [ ] /review-context loads efficiently

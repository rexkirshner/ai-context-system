# Claude Context System v2.2.0 - Revised Implementation Plan

**Core Insight:** Modern development is collaborative. Two programmers using AI need to understand each other's decisions, reasoning, and current work. The Context System must evolve from single-developer continuity to **team coordination protocol**.

**Philosophy:** "Enable human understanding through AI-documented reasoning"

**Status:** Revised Draft - Step-by-Step Implementation
**Created:** 2025-10-20
**Target Release:** v2.2.0

---

## Executive Summary

v2.2.0 transforms the Claude Context System from a single-developer tool to a **collaborative development protocol with repository boundaries**. Based on 20+ sessions of feedback and the recognition that developers work in teams within complex repository structures, this release focuses on:

✅ **Human-to-human understanding** through AI-documented decisions
🤝 **Collaboration features** that prevent conflicts and enable handoffs
🛡️ **Protection mechanisms** that preserve team trust and repository boundaries
📍 **Navigation aids** that help developers find each other's work
🔒 **Boundary containment** for monorepos and subdirectory projects
🗑️ **Bloat removal** to keep the system maintainable

**New Critical Feature:** Repository boundaries prevent the context system from accessing files outside its designated scope - essential for monorepos, subdirectory projects, and maintaining clean separation between multiple projects in one repository.

## Part 1: The Collaboration Reality Check

### What Actually Happens in Modern Development

**Scenario A: Two developers, one project, different AI tools**

```
Monday: Alice + Claude Code
- Works on backend API
- Makes architecture decision about caching
- Commits but doesn't push (waiting for tests)
- Ends session with mental model documented

Tuesday: Bob + Cursor
- Needs to understand Alice's caching decision
- Builds frontend assuming certain API behavior
- Makes his own decisions about state management
- References Alice's work in his reasoning

Wednesday: Alice + Claude Code
- Returns to find Bob's frontend work
- Needs to understand Bob's state assumptions
- Adjusts API to match Bob's needs
- Documents why the adjustment was made

Thursday: Code Review (Charlie + GitHub Copilot)
- Needs to understand BOTH Alice and Bob's reasoning
- Reviews not just code but decisions
- Suggests improvements based on full context
```

**Scenario B: Monorepo with multiple teams (NEW CHALLENGE)**

```
/company-monorepo
  /services
    /payment-api (Team A: High security, PCI compliance)
    /user-api (Team B: Different requirements)
    /frontend (Team C: UI team)

Problem WITHOUT boundaries:
- Team A's context system accidentally reads Team B's secrets
- Team B's /save command overwrites Team A's context
- Team C's AI assistant accesses payment-api code (security risk)
- Context systems conflict and contaminate each other

Solution WITH boundaries:
- Each team has isolated context within their subdirectory
- /init-context-scoped creates boundary at team level
- Team A's context CANNOT access ../user-api/
- Each team's AI assistant respects boundaries
- Clean separation, no contamination
```

**The Current Problems:**
1. **Single Project:** Alice's reasoning locked in her head
2. **Monorepo:** Teams' contexts contaminate each other
3. **Security:** AI assistants access sensitive areas
4. **Isolation:** No clean separation between projects

**The Solution: Context System as Bounded Collaboration Protocol**

### 3. Checkpoint Phrases - When to STOP

**These phrases indicate "complete task then STOP":**

```python
CHECKPOINT_PHRASES = [
    "before we continue",
    "before we move on",
    "first, let's",
    "once that's done",
    "after you finish",
    "when complete"

    "and then",
    "followed by",
    "next",
    "after that"
]

**Rule:** If instruction contains CHECKPOINT_PHRASE:

#### Step 1.5.2: Implement Boundary Checker

**File:** Create `.claude/scripts/boundary-check.sh`

```bash
#!/bin/bash

# Boundary enforcement for Claude Context System
# Prevents accessing files outside designated project boundary

# Load boundary config
CONTEXT_CONFIG="${PROJECT_ROOT:-.}/context/.context-config.json"
if [ ! -f "$CONTEXT_CONFIG" ]; then
  CONTEXT_CONFIG="$(find . -name ".context-config.json" 2>/dev/null | head -1)"
fi

# Parse boundary settings
BOUNDARY_ENABLED=$(jq -r '.boundary.enabled // false' "$CONTEXT_CONFIG")
PROJECT_ROOT=$(jq -r '.boundary.projectRoot // "."' "$CONTEXT_CONFIG")
ENFORCEMENT=$(jq -r '.boundary.enforcement // "warn"' "$CONTEXT_CONFIG")
MAX_PARENT_LEVELS=$(jq -r '.boundary.scanBoundary.maxParentLevels // 0' "$CONTEXT_CONFIG")

# Function: Check if path is within boundary
check_boundary() {
  local target_path="$1"
  local operation="$2"  # read/write/execute

  # Resolve absolute paths
  local abs_target=$(realpath "$target_path" 2>/dev/null)
  local abs_root=$(realpath "$PROJECT_ROOT")

  # Check if target is within project root
  if [[ "$abs_target" != "$abs_root"* ]]; then
    if [ "$ENFORCEMENT" = "strict" ]; then
      echo "❌ BOUNDARY VIOLATION: Attempted to $operation outside project boundary"
      echo "  Target: $target_path"
      echo "  Project boundary: $PROJECT_ROOT"
      echo "  This operation has been blocked."
      return 1
    else
      echo "⚠️  WARNING: Accessing file outside project boundary"
      echo "  Target: $target_path"
      echo "  Consider updating boundary config if this is intentional"
      return 0
    fi
  fi

  # Check parent directory traversal
  local parent_count=$(echo "$target_path" | grep -o '\.\.' | wc -l)
  if [ "$parent_count" -gt "$MAX_PARENT_LEVELS" ]; then
    echo "❌ BOUNDARY VIOLATION: Too many parent directory traversals"
    echo "  Path: $target_path"
    echo "  Max allowed: $MAX_PARENT_LEVELS"
    return 1
  fi

  # Check blocked paths
  local blocked_paths=$(jq -r '.boundary.blockedPaths[]?' "$CONTEXT_CONFIG")
  for blocked in $blocked_paths; do
    if [[ "$target_path" == *"$blocked"* ]]; then
      echo "❌ BOUNDARY VIOLATION: Path is explicitly blocked"
      echo "  Path: $target_path"
      echo "  Blocked pattern: $blocked"
      return 1
    fi
  done

  return 0
}

# Function: Safe file read (with boundary check)
safe_read() {
  local file="$1"

  if ! check_boundary "$file" "read"; then
    return 1
  fi

  cat "$file"
}

# Function: Safe file write (with boundary check)
safe_write() {
  local file="$1"
  local content="$2"

  if ! check_boundary "$file" "write"; then
    return 1
  fi

  echo "$content" > "$file"
}

# Function: Safe directory listing (with boundary check)
safe_ls() {
  local dir="${1:-.}"

  if ! check_boundary "$dir" "list"; then
    return 1
  fi

  ls -la "$dir"
}

# Export functions for use in other scripts
export -f check_boundary
export -f safe_read
export -f safe_write
export -f safe_ls
```

#### Step 3.3: Simplify Staleness Configuration

**File:** `config/.context-config.template.json`

**Current (Overengineered):**
```json
"stalenessThresholds": {
  "STATUS.md": {"green": 7, "yellow": 14, "red": 30},
  "SESSIONS.md": {"green": 7, "yellow": 14, "red": 21},
  // ... 20+ lines of config
}
```

**Simplified:**
```json
"staleness": {
  "enabled": true,
  "checkInterval": "daily",
  "warnAfter": {
    "default": 7,
    "stable": 90
  }
}
```

**Hardcode in `/validate-context`:**
```bash
# Simple staleness check
FREQUENT_FILES=("STATUS.md" "SESSIONS.md")
STABLE_FILES=("CONTEXT.md" "DECISIONS.md")

for file in "${FREQUENT_FILES[@]}"; do
  if file_older_than_days "$file" 7; then
    echo "⚠️ $file is stale (>7 days)"
  fi
done

for file in "${STABLE_FILES[@]}"; do
  if file_older_than_days "$file" 90; then
    echo "⚠️ $file is stale (>90 days)"
  fi
done
```

# Claude Context System v2.2.0 - Implementation Plan

**Philosophy:** "Fix what's broken, remove what's unused, resist what's not proven"

**Status:** Draft - Ready for Review
**Created:** 2025-10-20
**Target Release:** v2.2.0

---

## Executive Summary

v2.2.0 focuses on **reliability over features**. Based on 20+ sessions of real-world feedback across 3 production projects, this release:

✅ **Fixes critical issues** that cause real problems (git push violations, context loss)
🗑️ **Removes bloat** from v2.0/v2.1 that creates maintenance burden
📝 **Documents patterns** instead of enforcing features
🚫 **Rejects complexity** that doesn't earn its keep

**Key Metrics:**
- **3 critical bugs fixed** (appeared in all projects)
- **2 commands removed** (deprecated/unused)
- **0 new commands added** (resist feature creep)
- **~500 lines of code removed** (estimated)
- **~200 lines of code added** (enforcement only)

---

## Philosophy: The Anti-Bloat Principles

### 1. **Evidence-Based Changes Only**
- Require **2+ projects** reporting same issue before considering universal fix
- Single-project feedback → Document as optional pattern
- Speculation → Reject immediately

### 2. **Maintenance Cost vs Value**
- Every feature has ongoing cost (updates, docs, support)
- Only add if value >> maintenance burden
- Remove if cost > value

### 3. **Simple > Clever**
- Boring, reliable code beats clever abstractions
- Hard-coded checkpoints beat complex state machines
- Bash scripts beat language-agnostic solutions

### 4. **Document, Don't Enforce**
- Optional patterns in usage-examples.md
- Required structure stays minimal
- Let projects customize

### 5. **No Speculative Features**
- "We might need X someday" → NO
- "Users will want Y" → Wait for actual demand
- "This would be cool" → Reject

## Part 2: What to Fix (Critical Issues)

### 🔧 Fix #1: Git Push Protection (CRITICAL)

**Evidence:** 10+ violations across ALL 3 projects
**Impact:** Costs money, erodes trust, violates core principle
**Root Cause:** Documentation doesn't work, need structural prevention

#### Implementation: 5-Layer Defense

**Layer 1: Session Flag (Simple State)**
```bash
# In /review-context (Step 1.6 - already exists, just enforce)
PUSH_APPROVED=false

# Before any git push in ANY command:
if [ "$PUSH_APPROVED" = false ]; then
  echo "⚠️  STOP: Git push requires explicit approval"
  echo "User must say: 'push', 'deploy', 'push to github'"
  echo "Aborting push operation."
  exit 1
fi
```

**Layer 2: Pre-Push Checklist (Mandatory in /save-full)**
```markdown
## Step 8: Git Operations (Enhanced)

**BEFORE git push, verify:**
- [ ] Did user's LAST message contain: "push", "deploy", "push to github"?
- [ ] If NO → Ask: "Ready to push? This will trigger deployment. (yes/no)"
- [ ] If user says NO → Skip push, report "Committed locally only"
- [ ] If user says YES → Log approval quote, set PUSH_APPROVED=true, then push

**In SESSIONS.md, log:**
```markdown
### Git Operations
- **Commits:** 1 commit (abc123)
  - [commit message]
- **Pushed:** YES/NO
- **Approval:** "[exact quote]" or "Not pushed - user will push manually"
```

**Layer 3: Checkpoint Phrase Detection**
```bash
# List of phrases that mean "STOP after this task"
CHECKPOINT_PHRASES=(
  "before we continue"
  "before we move on"
  "first, let's"
  "once that's done"
)

# After completing task, check user's original instruction
# If contained checkpoint phrase → Stop and wait
# Do NOT continue to next logical step
```

**Layer 4: Commit ≠ Push (Default Behavior Change)**
```bash
# OLD (v2.1): git commit && git push
# NEW (v2.2): git commit (stop here)

# After commit:
echo "✅ Commit created: [hash] [message]"
echo ""
echo "📋 To push to GitHub, say:"
echo "  - 'push'"
echo "  - 'push to github'"
echo "  - 'deploy'"
echo ""
echo "Or run 'git push' manually when ready."
```

**Layer 5: Validation Audit**
```bash
# In /validate-context, check git history
git log --since="24 hours ago" --oneline

# If commits exist:
echo "Found X commits in last 24 hours."
echo "Were these pushed with user approval?"
echo "Check SESSIONS.md Git Operations section for approval quotes."

# Flag if SESSIONS.md missing approval documentation
```

- `.claude/commands/save.md` (add pre-push checklist)

### 🔧 Fix #3: Context Folder Location Detection (MEDIUM)

**Evidence:** 1 project, but common failure mode
**Impact:** Commands fail when pwd is subdirectory
**Root Cause:** Commands assume `context/` is in current directory

#### Implementation: Path Resolution

```bash
# Add to ALL commands that access context/

find_context_dir() {
  if [ -d "context" ]; then
    echo "context"
  elif [ -d "../context" ]; then
    echo "../context"
  elif [ -d "../../context" ]; then
    echo "../../context"
  else
    echo "❌ Error: context/ directory not found"
    echo "Searched: ./ ../ ../../"
    echo "Run this command from project root or subdirectory (max 2 levels deep)"
    exit 1
  fi
}

CONTEXT_DIR=$(find_context_dir)

# Use $CONTEXT_DIR instead of hardcoded "context/"
# Example: cat "$CONTEXT_DIR/STATUS.md"
```

## Part 4: What NOT to Add (Feature Rejection)

### 🚫 Reject #1: New Slash Commands

**Proposals from feedback:**
- `/find [keyword]` - Cross-file search
- `/map [feature]` - Show code locations
- `/status-check` - Health check
- `/organize-docs` - Doc management

**Rejection Rationale:**
- Existing tools work (grep, IDE search, git status)
- Feature creep
- Maintenance burden (12 commands already)
- Not proven essential (single project suggestions)

**Alternative:** Users can use standard tools
- Search: `grep -r "keyword" context/`
- Status: `git status && npm test`
- Organization: Manual cleanup

---

### 🚫 Reject #2: Keyword Index (KEYWORDS.md)

**Proposal:** File mapping topics to locations

**Rejection Rationale:**
- High maintenance (manual updates)
- Goes stale quickly
- Cmd+F works fine
- Creates duplication

**Alternative:** Use IDE search or grep

---

### 🚫 Reject #3: Split CONTEXT.md

**Proposal:** CONTEXT → SETUP + ARCHITECTURE + METHODOLOGY

**Rejection Rationale:**
- Only 1 project complaint (600-line file)
- Adds navigation complexity (1 file → 4 files)
- Cmd+F solves scanning problem
- CONTEXT.md is meant to be comprehensive

**Alternative:** Users can organize sections within CONTEXT.md

---

### 🚫 Reject #4: TESTING.md Requirement

**Proposal:** Centralized testing documentation

**Rejection Rationale:**
- Very project-specific
- Testing docs belong in project README
- Not part of context continuity
- Adds required file for minimal benefit

**Alternative:** Users can create if needed, don't enforce

## Part 7: Migration Path (v2.1 → v2.2)

### Automatic Migration

**When user runs `/update-context-system`:**

1. **Detect v2.1 installation**
   - Check `.context-config.json` version field
   - If "2.1.0" → proceed with v2.2 migration

2. **Remove deprecated files**
   - Delete `.claude/commands/save-context.md` if exists
   - Delete `.claude/docs/save-context-guide.md` if exists

3. **Simplify config**
   - Migrate `.context-config.json`:
     ```bash
     # OLD (v2.1): Complex staleness thresholds
     # NEW (v2.2): Simple enabled/disabled

     # Auto-convert to simplified format
     # Keep user's "enabled" preference
     # Remove per-file thresholds
     ```

4. **Update version**
   - Set `"version": "2.2.0"` in config

5. **Report changes**
   ```
   ✅ Updated to v2.2.0

   Changes:
   - Removed deprecated /save-context command
   - Simplified staleness configuration
   - Enhanced git push protection
   - Made session TL;DR mandatory

   No action required - your project is ready.
   ```

### Manual Steps (Optional)

**If user wants to adopt new patterns:**

1. **Add CODE_MAP.md** (optional)
   - Copy from `templates/CODE_MAP.template.md`
   - Customize for project

2. **Organize docs** (optional)
   - Follow best practices in usage-examples.md
   - Create docs/ and artifacts/ structure

3. **Add visual diagrams** (optional)
   - See examples in usage-examples.md
   - Add to ARCHITECTURE.md or CONTEXT.md

### Breaking Changes

**None** - v2.2.0 is backward compatible with v2.1.0

**Behavior Changes:**
- Git push now requires explicit approval (was: documentation-based)

- `/save-context` command removed (was: deprecated)

## Part 10: Risk Assessment & Mitigation

### Risk #1: Git Push Protection Too Strict

**Risk:** Users get annoyed by constant approval prompts
**Likelihood:** Medium
**Impact:** Medium (user frustration)

**Mitigation:**
- Clear messaging: "This prevents accidental deploys"
- Easy approval: Just say "push"
- Session flag: Approve once per session if desired
- Escape hatch: Users can disable in config

### Risk #2: TL;DR Requirement Feels Bureaucratic

**Risk:** Users skip `/save-full` to avoid writing TL;DR
**Likelihood:** Low
**Impact:** Low (can still use `/save`)

**Mitigation:**
- Only required for `/save-full` (not `/save`)
- 2-3 sentences (not essay)
- Template provided
- Explain value: "Enables session continuity"

### Risk #3: Removing Files Breaks Existing Projects

**Risk:** Projects using deprecated commands break
**Likelihood:** Very Low
**Impact:** Low (easy to fix)

**Mitigation:**
- Deprecated since v2.1 (plenty of warning)
- Migration guide clear
- Backup created automatically
- Easy rollback

### Risk #4: Users Want Rejected Features

**Risk:** Demand for `/find`, KEYWORDS.md, etc.
**Likelihood:** Medium
**Impact:** Low (can always add later)

**Mitigation:**
- Document rationale clearly
- Show alternatives that work
- Open to revisiting with evidence
- Keep issue tracker for requests
